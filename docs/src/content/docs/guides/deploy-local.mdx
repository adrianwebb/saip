This guide walks you through running SAIP on a single local machine with a consumer or workstation GPU. Local deployment is ideal for development, testing, and small-scale inference workloads.

## Hardware Requirements

SAIP ships two **service profiles**, chosen by the VRAM and compute capability of the
GPU in the machine. Each profile declares a ceiling for one service stack, backed by
measurements — see [Hardware Profiles](/saip/reference/hardware-profiles/) for the numbers
and the repro commands.

| Component | Minimum (inference only) | Minimum (full loop) | Recommended |
|-----------|--------------------------|---------------------|-------------|
| GPU VRAM | 8 GB (`inference-8gb`) | 12 GB (`full-loop-12gb`) | 16 GB+ |
| Compute capability | 7.5 (inference) | 8.0 (Ampere — bf16 training) | 8.9+ (Ada) |
| System RAM | 16 GB | 32 GB | 32 GB |
| Disk | 50 GB free | 80 GB free | 100 GB SSD |
| CUDA | 12.1+ | 12.4+ | 12.4+ |

- **8 GB — inference only.** The gateway serves Qwen3.5-4B (AWQ 4-bit, text-only) with
  four LoRA adapter slots live. The learning loop still *collects* data on this tier; it
  does not train.
- **12 GB — the full loop.** Both the inference and training profiles fit the same card,
  time-shared through
  [awake/sleep mode](/saip/explanation/architecture/#awakesleep-mode-single-gpu-time-sharing).

:::caution[VRAM Warning]
SAIP requires at least **8 GB of VRAM** to serve and **12 GB** to fine-tune locally.
Integrated GPUs and older cards below those floors fail during model loading with an OOM
error. Note that `--gpu-memory-utilization` is computed against the card's **total**
memory and startup aborts if *free* memory at launch falls below that product — so a
desktop compositor or browser holding VRAM lowers the ceiling you can actually use, and
the flag must be derived rather than fixed. Check what you have before proceeding:

```bash
nvidia-smi --query-gpu=name,memory.total,memory.free --format=csv,noheader
```
:::

:::note[Training on a 12 GB card]
12 GB is the floor for local fine-tuning, not a comfortable margin. QLoRA (4-bit)
training on the Qwen3.5 family is discouraged by its maintainers because of unusually
large quantization differences, and bf16 LoRA on the 4B model measures roughly 10 GB at
2048-token sequences before optimizer state. Short sequences, gradient checkpointing, and
8-bit optimizers keep it inside 12 GB. If you need longer contexts, rent GPU hours and
train remotely — see [Deploy on Hyperstack](/saip/guides/deploy-hyperstack/).
:::

## Prerequisites

### Docker & NVIDIA Container Toolkit

SAIP runs inside Docker containers with GPU passthrough. Install both components:

1. **Install Docker Engine** (not Docker Desktop):

```bash
# Ubuntu/Debian
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
newgrp docker
```

2. **Install NVIDIA Container Toolkit**:

```bash
# Add the NVIDIA package repository
distribution=$(. /etc/os-release; echo $ID$VERSION_ID)
curl -s -L https://nvidia.github.io/libnvidia-container/gpgkey | sudo apt-key add -
curl -s -L https://nvidia.github.io/libnvidia-container/$distribution/libnvidia-container.list \
  | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

sudo apt update && sudo apt install -y nvidia-container-toolkit
```

3. **Verify GPU access inside Docker**:

```bash
docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi
```

You should see your GPU listed in the output. If this command fails, troubleshoot the toolkit installation before continuing.

:::tip[Docker Group]
If you get a permission denied error when running `docker`, log out and back in after adding yourself to the `docker` group, or run `newgrp docker` in your current shell.
:::

## Configuration

### Create Your `.env` File

Copy the example environment file and fill in your values:

```bash
cp .env.example .env
```

Required variables for local deployment:

```ini
# Cloudflare R2 storage for adapters, knowledge, sessions, feedback
SAIP_R2_BUCKET=saip-local
SAIP_R2_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
SAIP_R2_ACCESS_KEY_ID=your-access-key
SAIP_R2_SECRET_ACCESS_KEY=your-secret-key

# HuggingFace Hub token for downloading base models
SAIP_HF_TOKEN=hf_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

:::note[Bucket Naming]
For local deployments, use a dedicated R2 bucket (e.g., `saip-local`) to avoid conflicts with remote training nodes that may write to the same storage.
:::

### Select a Service Profile

The profile selects the engine arguments, the VRAM ceiling, and the KV-cache dtype your GPU
can safely use. It is resolved automatically from the card, so `saip.yaml` leaves it unset:

```yaml
# profile: inference-8gb   # uncomment to pin a tier (or: full-loop-12gb)
```

Pinning is for holding a machine down on purpose — CI, a GPU shared with other workloads, or
reproducing a report. On a 16 GB dev machine a pinned `inference-8gb` will quietly cap you at
the smaller tier, so check what resolved before concluding a tier is slow.

If `profile` is omitted, SAIP probes the GPU (`nvidia-smi`) and picks the highest tier the
card satisfies, then **fails closed** with a named error if none fits — rather than
letting the engine OOM minutes later. Override per invocation with
`saip awake --profile <name>`, and inspect what was resolved with `saip profiles`.

The profile, not the user, owns these settings; the values below are shown for clarity:

| Setting | `inference-8gb` | `full-loop-12gb` |
|---------|-----------------|------------------|
| `max_model_len` | 24,576 | 65,536 |
| `kv_cache_dtype` | `auto` (16-bit) | `auto` (16-bit) |
| `language_model_only` | `true` | `true` |
| `enforce_eager` | `true` | `false` |
| `max_loras` / `max_lora_rank` | 4 / 16 | 4 / 16 |
| VRAM ceiling | 7.0 GiB | 11.0 GiB |

`gpu_memory_utilization` is **derived**, not configured: the profile divides its ceiling
by the card's total memory and checks the result against measured free memory at launch.

### Verify R2 Connectivity

Before starting services, confirm your R2 credentials work:

```bash
aws s3 ls s3://${SAIP_R2_BUCKET}/ \
  --endpoint-url ${SAIP_R2_ENDPOINT} \
  --access-key ${SAIP_R2_ACCESS_KEY_ID} \
  --secret-key ${SAIP_R2_SECRET_ACCESS_KEY}
```

If this returns an error, double-check your credentials and endpoint URL. See [Troubleshooting](#r2-connection-failures) below.

## Running SAIP

### Start Services (`saip awake`)

The `awake` command pulls images, downloads the model from R2, and starts the inference server:

```bash
saip awake
```

Expected output:

```
[awake] Pulling inference image... done
[awake] Profile: inference-8gb (RTX 3080 Laptop, 15.58 GiB total, 13.4 GiB free)
[awake] Syncing model from R2 (QuantTrio/Qwen3.5-4B-AWQ)... done (5.7 GB)
[awake] Starting inference container on GPU 0... running
[awake] Health check passed — API available at http://localhost:8000/v1
```

:::tip[First Run]
The first `saip awake` downloads the model weights from R2, which can take 5–15 minutes depending on your connection. Subsequent starts skip this step if the local cache is intact.
:::

### Stop Services (`saip sleep`)

Gracefully shut down inference while preserving cached models:

```bash
saip sleep
```

This stops containers but keeps downloaded models on disk so the next `awake` starts faster.

### Full Teardown (`saip down`)

Remove containers, volumes, and cached models:

```bash
saip down
```

Use this when switching models or troubleshooting a corrupted state.

## GPU Monitoring

Monitor GPU utilization while SAIP is running:

```bash
# Continuous monitoring (refresh every 1 second)
watch -n 1 nvidia-smi

# One-shot query for scripting
nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total,temperature.gpu \
  --format=csv,noheader
```

:::tip[vLLM Metrics]
SAIP exposes Prometheus metrics at `http://localhost:8000/metrics`. Key metrics to watch:
- `vllm:gpu_cache_usage_perc` — KV cache utilization (high = near capacity)
- `vllm:num_requests_running` — active inference requests
- `vllm:avg_generation_throughput_tokens_per_s` — tokens generated per second
:::

## Troubleshooting

### Out of Memory (OOM)

**Symptoms:** Container exits with `CUDA out of memory`, `torch.cuda.OutOfMemoryError`, or
vLLM refuses to start with `Free memory on device ... is less than desired GPU memory
utilization`, or `No available memory for the cache blocks`.

**Solutions:**
1. Confirm the card meets the tier you selected: 8 GB for `inference-8gb`, 12 GB for
   `full-loop-12gb` (see [Hardware Profiles](/saip/reference/hardware-profiles/)).
2. Close other GPU-consuming processes — `nvidia-smi` lists PIDs holding VRAM. Because
   utilization is computed against **total** memory but must fit inside **free** memory,
   a browser or compositor alone can make a compliant card fail.
3. Lower `SAIP_MAX_MODEL_LEN`. On this model only 8 of 32 layers hold a KV cache, so
   context is comparatively cheap (~35 KiB/token at bf16) — but it is still the main
   dial: 24,576 tokens costs roughly 0.9 GiB.
4. Override the derived ceiling with `SAIP_GPU_MEMORY_UTILIZATION` (a fraction of *total*
   VRAM). Normally you should not need to: the active profile derives this value from
   measured free memory. Set it only to go **down**, e.g. `0.40` on a shared 16 GB card.
5. On an 8 GB card, keep `enforce_eager: true` in the profile. CUDA graph capture costs
   about 2.6 GiB on this model — the single largest optional item in the budget.
6. Fewer adapter slots cost less: each LoRA slot is resident VRAM. Drop
   `max_loras` from 4 to 2 to reclaim roughly 0.25 GiB.

:::danger[Do not enable 8-bit KV cache on Ampere or older]
It is tempting to buy back VRAM with `kv_cache_dtype: int8_per_token_head` or `fp8`. On
compute capability below 8.9 these are either rejected outright (fp8: *"native FP8
(fp8e4nv) requires SM89+"*) or, in the case of `int8_per_token_head`, **accepted, report
a larger cache, and produce corrupted output with no error**. SAIP's profile validator
forbids both below SM 8.9. Use `kv_cache_dtype: auto` (16-bit) there. See
[Hardware Profiles → KV cache dtype by capability](/saip/reference/hardware-profiles/).
:::

### CUDA Errors

**Symptoms:** `CUDA error: device-side assert triggered` or `no kernel image is available for execution on the device`.

**Solutions:**
1. Verify CUDA compatibility: `nvidia-smi` shows the driver CUDA version; it must be ≥ the container's CUDA version.
2. Update NVIDIA drivers: `sudo apt install --only-upgrade nvidia-driver-*`.
3. Restart the Docker daemon after driver updates: `sudo systemctl restart docker`.
4. Run `saip down && saip awake` to rebuild containers against the new driver.

### R2 Connection Failures

**Symptoms:** `AccessDenied`, `NoSuchBucket`, or timeout errors during `saip awake`.

**Solutions:**
1. Verify credentials are correct and not expired.
2. Confirm the bucket exists and your key has read/write permissions.
3. Check that `SAIP_R2_ENDPOINT` uses the correct regional endpoint (not the global S3 endpoint).
4. Test connectivity outside Docker first (see [Verify R2 Connectivity](#verify-r2-connectivity)).
5. If behind a proxy, set `HTTPS_PROXY` in your `.env`.

:::caution[Credentials in Logs]
Never paste full R2 credentials into issue reports or chat. Redact keys to their last 4 characters (e.g., `...a3f9`) when sharing error output.
:::

### Container Won't Start

**Symptoms:** `docker: Error response from daemon: could not select device driver "" with capabilities: [[gpu]]`.

**Solutions:**
1. Confirm NVIDIA Container Toolkit is installed: `dpkg -l | grep nvidia-container-toolkit`.
2. Restart Docker: `sudo systemctl restart docker`.
3. Verify the runtime is configured: `cat /etc/docker/daemon.json` should include `"nvidia"` in runtimes.
4. Reinstall the toolkit if the runtime entry is missing.
