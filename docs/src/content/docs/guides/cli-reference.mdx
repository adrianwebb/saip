The `saip` CLI manages SAIP services, models, and infrastructure. All commands operate relative to the project root directory where `.env` and `saip.yaml` reside.

## Installing the CLI

`saip` is the `@saip/cli` package's bin entry. It is **not published to npm**, so `npx saip`
cannot resolve it and `npm i -g saip` would install an unrelated package. Install it from
this repository.

```bash
pnpm install && pnpm -r build          # compiles every package; dist/ is the runnable output
pnpm --filter @saip/cli install:local   # links saip onto your PATH
saip --version
```

`install:local` rather than `link`: pnpm owns the `link` subcommand and intercepts it before your
package script is reached. The script symlinks `cli/dist/index.js` into the first writable
directory on your PATH among `pnpm bin -g`, `~/.local/bin`, and `~/.local/share/pnpm/bin`, and
prints what it linked.

It must be a **symlink**, not a hard link or a copy: a hard link is an ordinary file sitting in
the bin directory, so Node resolves `node_modules` upward from *there* and fails to find
`cordis`. And `@saip/cli` depends on `@saip/shared` through the `workspace:` protocol, which a
global install cannot resolve at all — so linking against a checkout is the supported install
until single-file binaries land.

The binary resolves `@saip/shared` through the workspace, so a global *install* of the
package (as opposed to a link) cannot work while that dependency uses the `workspace:`
protocol. Standalone single-file binaries for each architecture are tracked separately;
until then, install from a checkout.

### Installing a released binary

<DownloadButtons />

> Binaries are attached automatically to every release from **0.6.0** onward (the workflow landed in
> #111); older tags were published by hand and carry none.

Each release publishes one self-contained executable per platform — **no Node.js, no pnpm, no source
checkout** on the server:

| Artifact | Platform |
|---|---|
| `saip-linux-x64` | Linux, x86-64 |
| `saip-linux-arm64` | Linux, ARM64 (cloud ARM instances, Raspberry Pi 4/5) |
| `saip-darwin-x64` | macOS on Intel |
| `saip-darwin-arm64` | macOS on Apple Silicon |
| `saip-windows-x64.exe` | Windows |

```bash
BASE=https://github.com/adrianwebb/saip/releases/latest/download
curl -fLO $BASE/saip-linux-x64
curl -fLO $BASE/SHA256SUMS
sha256sum -c SHA256SUMS --ignore-missing          # verify before running anything
chmod +x saip-linux-x64
mv saip-linux-x64 ~/.local/bin/saip
saip --version                                    # must print the release's version
```

A release that publishes no assets is a failed release, not an empty one: CI runs each platform's
binary and refuses to publish if any artifact or its `--version` check is missing, so a partially
uploaded release cannot be produced silently.

macOS blocks an unsigned download on first run: `xattr -d com.apple.quarantine ./saip-darwin-arm64`
**after** checking the checksum, or approve it in System Settings. The binary reports the version it
was built from; a build whose embedded version does not match the release refuses to compile.

### Where it looks for configuration

`saip` locates `saip.yaml` and `hosts.yaml` by **walking up from the current directory**, so
it works from a project root, a subdirectory, or anywhere else you happen to be standing.
An explicit path always wins:

| Setting | Used for | Resolution |
|---------|----------|------------|
| `SAIP_CONFIG` | `saip.yaml` | explicit path if set, else nearest `saip.yaml` upward from cwd |
| `SAIP_HOSTS_FILE` | `hosts.yaml` | explicit path if set, else nearest `hosts.yaml` upward from cwd |

Every command that reads configuration **prints the file it loaded**. With a global install
the dangerous failure is not "cannot find config" but "silently used another project's
config", so the resolved path is part of normal output rather than a debug flag.

## `saip ssh`

SAIP-generated, SAIP-stored SSH keypairs, one per host. No `ssh-keygen`, no key files to lose.

```bash
saip ssh <generate|show|verify|rotate|remove|migrate> --host <name>
```

| Command | What it does |
|---|---|
| `saip ssh generate --host X` | Creates an Ed25519 keypair. Private half goes into the encrypted store as `SAIP_SSH_KEY_X`; public half is written next to it. Refuses to overwrite an existing key — use `rotate`. |
| `saip ssh show --host X` | Prints the **public** key only. Safe to paste into a provider console or pipe anywhere. |
| `saip ssh verify --host X` | Attempts authentication with the managed key in `BatchMode`, so it fails fast and never hangs on a password prompt. |
| `saip ssh rotate --host X` | Replaces the keypair. The old private half is gone from the store; the old **public** key stays authorised on the host until you revoke it there — the command says so, because SAIP cannot revoke a key it does not control. |
| `saip ssh remove --host X` | Deletes the managed key and its public file. |
| `saip ssh migrate` | Moves a legacy `SAIP_SSH_PRIVATE_KEY` value into a managed per-host key and clears the old name. |

The private key is materialised as a temporary `0600` file only for the duration of an SSH call and
removed on every exit path, including interruption and signals. `Ctrl+C` is handled explicitly: raw
mode disables `ISIG`, so a keypress arrives as a byte and nothing would otherwise clean up.

## How output is presented

`saip config init` and `saip config help` render each credential as a **card** when you are at a
terminal, and as plain `label: value` lines everywhere else. The same fields and the same wording
either way — presentation is the only thing that changes, so a log line and a card cannot disagree.

```
╭────────────────────────────────────────────────────────────────╮
│ SAIP_R2_BUCKET  (required)                                     │
│ what: Object storage for adapters, knowledge, sessions and      │
│ feedback. Everything the platform persists lives here.         │
│ scoping: One private bucket per deployment is enough. Do not   │
│ make it public: adapter weights and user data go in it.        │
│ create: https://dash.cloudflare.com/?to=/:account/r2/overview  │
╰────────────────────────────────────────────────────────────────╯
```

The fallback is automatic, never a flag:

| Situation | What you get |
|---|---|
| Piped, redirected, CI, agent | plain lines — greppable, and **no box-drawing characters at all** |
| `TERM=dumb` or a non-UTF-8 locale (`LANG=C`) | ASCII frame (`+----+`) if a frame is drawn at all |
| `NO_COLOR`, or not a TTY | no ANSI escapes, ever |
| Terminal narrower than ~72 columns | labels and values stack instead of sharing a line |
| 100+ columns | width is clamped so a giant terminal does not produce a giant card |

**Why this is hand-rolled rather than Ink.** An earlier version of this note said Ink could not be
bundled. **That was wrong**, and the mistake is worth keeping visible: every failure came from my
setup, not from Ink. Re-measured with the configuration attached:

| Setup | Result |
|---|---|
| plain Node, unbundled | **works**, including into a pipe (no cursor control sequences) |
| esbuild bundle | **fails**: unresolved `react-devtools-core`; with it stubbed, `Dynamic require of "…"` at runtime |
| `bun build --compile`, `react-devtools-core` installed | **works**: ~92.7 MB binary, renders under a pty; ~0.7 MB over a plain Bun binary |
| `bun build --compile` without it | fails to resolve — the exact error I had reported as a limit of Ink |
| `TERM=dumb` | Ink does **not** degrade: box-drawing characters either way |
| compiled Bun binary, piped | writes **nothing** — a property of that artifact, not of Ink |

So the hand-rolled renderer ships for a weaker but honest reason: no dependencies, identical
behaviour in every row above, and a deliberate plain-text path for non-TTY output. If Bun becomes
the packager ([#71](https://github.com/adrianwebb/saip/issues/71)), Ink for interactive use with
this as the fallback is a live option rather than a rejected one.

### `saip` vs `saip-dev` — which build you are running

Two names, deliberately, because the two builds behave differently and "works in dev, broken on the
server" is this project's most repeated defect class:

| Command | What it is | How to get it |
|---|---|---|
| `saip` | the **source** build: `cli/dist/bin.js` symlinked by `pnpm --filter @saip/cli install:local`, runs on Node, tracks your working tree | use it while developing |
| `saip-dev` | a **compiled Bun binary** for your architecture, installed to `~/.local/bin/saip-dev` | `pnpm --filter @saip/cli install:dev` |
| release binary | the same compiled artifact, downloaded with `SHA256SUMS` | see "Installing a released binary" above |

`saip-dev` is what a server runs, so it is what a change should be accepted against — especially the
terminal behaviour that cannot be judged from a test log: the wizard printing each value's explanation
**before** its prompt, and **paste** working, because most credential values are copied rather than typed.

```bash
pnpm --filter @saip/cli install:dev     # build host binary, install, execute it, write provenance
saip-dev --version                      # the version it was built from
saip-dev --built                        # commit, target, builtAt — what this artifact actually is
saip-dev config init                    # the acceptance test, at a real terminal
```

Notes that matter:

- The install runs the **same** build script as the release, so the version-parity guard applies: if
  `cli/src/version.ts` and `cli/package.json` disagree, the install refuses instead of shipping a binary
  that reports the wrong version.
- It **executes** what it installed and checks the reported version before calling the install a success.
  A copy that runs nowhere is not an install.
- It will **not** overwrite a `saip-dev` that it did not install (no matching provenance file) unless you
  pass `--force`. An unrelated file at that path is yours, not ours to replace.
- `SAIP_DEV_BINDIR` overrides the destination — used by the tests to install into a temp directory, and
  available if you want dev builds elsewhere.
- `--built` prints commit provenance recorded at compile time. A binary on a server is often the only
  copy of the application, so "which release" (`--version`) and "which commit" (`--built`) are the whole
  audit trail.

### Building a binary yourself

```bash
pnpm --filter @saip/shared build          # binaries bundle from source against built @saip/shared
pnpm --filter @saip/cli build:bin         # this host's architecture, then executes it as proof
pnpm --filter @saip/cli build:bin:all     # all five targets from one machine
```

Output lands in `cli/dist/binaries/` with `SHA256SUMS`. Notes that matter when changing this:

- **Bun is pinned and invoked through `npx`, not added as a dependency.** `pnpm add -D bun` did
  something worse than installing a package: pnpm wrote `devEngines.packageManager = "bun"` into
  `cli/package.json`, declaring Bun as this project's package manager. A build tool must not be able
  to change that by being installed.
- **Only the host target is executed by the build script.** Cross-compiled binaries are labelled
  `NOT executed (foreign architecture)`, and CI's matrix job runs each architecture on a native
  runner. "Built" is not evidence that a binary runs.
- The compiled entry point is `src/bin.ts`, and it must stay unconditional. #101 removed entry
  detection because a compiled binary's `process.argv[1]` is a virtual `/$bunfs/...` path, which no
  path comparison can resolve.

### `--json` — machine output is a guarantee, not a per-command feature

Every SAIP command accepts `--json`. The rule (#113):

> stdout of a `--json` run is **valid JSONL** — one parseable record per line — or the command says
> why it cannot be, as a JSON record, with a non-zero exit.

That means, for a script or agent:

- **Commands that emit records** (`status`, `profiles`) put blocks on stdout: `{"kind":"keyValues",…}`,
  one compact line each. Nothing else ever reaches stdout — provenance lines like
  `[saip] config: /path/saip.yaml` go to **stderr**, because they are diagnostics, not payload.
- **Commands that have not migrated yet** answer with a single record and exit **2**:

  ```json
  {"kind":"line","level":"error","text":"command "awake" does not emit --json records yet; …",
   "data":{"code":"not_structured","command":"awake"}}
  ```

  and **do not run**: `saip awake --json` switches nothing, because the guard short-circuits before the
  action. Ask for machine output from a side-effecting command and you get a refusal, not a deployment.

An empty stdout is deliberately treated as a failure of this guarantee, since a consumer cannot tell
"nothing to report" from "broken stream" — including when a command throws part way through, which
still writes one `command_failed` record before exiting non-zero.

**Scope of the guarantee:** it applies to a *valid invocation*. `saip ssh --json` with no subcommand is
a commander usage error — a message on stderr and exit 1 — and produces no record, because no command
ran. Distinguishing "you asked badly" from "the tool broke" is the caller's job, and the exit codes do
that: 2 for refused/unsupported, 1 for failure, 0 for success.

**Why it is enforced in the dispatcher rather than in each command:** release `0.5.0` shipped
`saip profiles --json` printing its provenance line immediately *before* the JSON body. The JSON was
valid; the stream was not; no test noticed, because every test parsed the JSON and ignored stdout. Ten
commands each remembering one rule is how that happened.

```bash
saip status --json     | jq -r '.rows[] | "\(.label)=\(.value)"'
saip profiles --json   | jq .resolution.profile
saip awake --json; echo $?        # 2 — refused as a record, nothing deployed
```

## `saip awake`

Start SAIP services and load the model into GPU memory.

### Synopsis

```bash
saip awake [--bucket <name>] [--profile <name>] [--model <identifier>] [--gpu <device>]
```

### Options

| Flag | Default | Description |
|------|---------|-------------|
| `--bucket <name>` | `$R2_BUCKET_NAME` | R2 bucket to sync models and adapters from |
| `--profile <name>` | auto-resolved | Service profile to run (`inference-8gb` or `full-loop-12gb`). Overrides `saip.yaml`; without it, the GPU is probed and the highest tier the card satisfies is chosen. Fails with exit 2 if no profile fits. |
| `--model <identifier>` | `$SAIP_MODEL` | Model to load (overrides `.env`) |
| `--gpu <device>` | `$SAIP_GPU_DEVICE` | GPU device index (overrides `.env`) |
| `--no-sync` | false | Skip R2 model sync; use local cache only |
| `--port <port>` | 8000 | API listen port |

### What It Does

1. **Validates configuration** — checks `.env` for required variables and verifies GPU availability.
2. **Resolves the service profile** — probes the GPU for name, total/free VRAM, and compute capability; selects the tier; rejects any `kv_cache_dtype` the card cannot use; derives `gpu_memory_utilization` from measured free memory.
3. **Pulls Docker images** — pulls the inference container image if not cached locally.
4. **Syncs model from R2** — downloads model weights and adapter files from the specified bucket (skipped with `--no-sync`).
5. **Starts inference container** — launches the vLLM server with GPU passthrough.
5. **Runs health check** — polls `/health` until the server responds or times out (60s default).
6. **Reports readiness** — prints the API endpoint and loaded model info.

### Example Output

```
$ saip awake --bucket saip-production
[awake] Validating configuration... OK
[awake] GPU 0: NVIDIA RTX A4000 (16 GB VRAM, 4.2 GB free, compute capability 8.6)
[awake] Resolving profile... full-loop-12gb (ceiling 11.0 GiB; free 4.2 GiB is below it)
[awake] Deriving gpu_memory_utilization... 0.26 (free VRAM minus headroom, over total)
[awake] Pulling saip-inference:v0.3.1... done (cached)
[awake] Syncing model from R2 (saip-production)...
  ├─ QuantTrio/Qwen3.5-4B-AWQ ... 5.7 GB ✓
  ├─ adapters/general@000042 ... 128 MB ✓
  └─ adapters/coding@000018 ... 96 MB ✓
[awake] Starting inference container... running (pid 48291)
[awake] Waiting for health check... ✓ (8.3s)
[awake] Ready — http://localhost:8000/v1
  Model: QuantTrio/Qwen3.5-4B-AWQ
  Profile: full-loop-12gb
  Adapters: general@000042, coding@000018 (4 slots, rank 16)
  Max context: 65536 tokens
  KV cache: auto (16-bit — fp8/int8 forbidden below compute capability 8.9)
```

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | Services started successfully |
| 1 | Configuration error (missing env var, invalid YAML, invalid profile) |
| 2 | GPU unavailable or insufficient VRAM (names the measured deficit and the tier's ceiling) |
| 3 | R2 sync failed (network, auth, or missing bucket) |
| 4 | Health check timeout (container started but API unresponsive) |

## `saip sleep`

Gracefully stop SAIP services while preserving cached models and data.

### Synopsis

```bash
saip sleep [--bucket <name>]
```

### Options

| Flag | Default | Description |
|------|---------|-------------|
| `--bucket <name>` | `$R2_BUCKET_NAME` | R2 bucket (used for final adapter sync-back) |
| `--force` | false | Skip graceful shutdown; kill containers immediately |
| `--no-sync-back` | false | Skip uploading local adapter changes to R2 |

### What It Does

1. **Drains active requests** — waits for in-flight inference requests to complete (30s timeout).
2. **Syncs adapter changes** — uploads any locally modified adapters back to R2 (skipped with `--no-sync-back`).
3. **Stops containers** — sends SIGTERM to the inference container; waits up to 15s before SIGKILL.
4. **Preserves cache** — model weights and adapter files remain on disk for fast restart.
5. **Reports status** — confirms clean shutdown.

### Example Output

```
$ saip sleep
[sleep] Draining active requests... 2 in-flight, waiting...
[sleep] Requests drained (3.1s)
[sleep] Syncing adapter changes to R2... no changes
[sleep] Stopping inference container (pid 48291)... stopped
[sleep] Services stopped. Cache preserved at ~/.cache/saip/
  Next 'saip awake' will skip model download.
```

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | Services stopped cleanly |
| 1 | No running services found |
| 2 | Drain timeout (requests still active after 30s; use `--force`) |
| 3 | R2 sync-back failed |

:::tip[Sleep vs Down]
Use `sleep` for temporary pauses (overnight, between experiments). Use `down` when switching models, updating SAIP, or troubleshooting corrupted state. `sleep` preserves the local cache; `down` removes it.
:::

## `saip down`

Fully tear down SAIP services and remove all local caches.

### Synopsis

```bash
saip down [--purge-cache]
```

### Options

| Flag | Default | Description |
|------|---------|-------------|
| `--purge-cache` | true | Remove cached model weights and adapters |
| `--keep-images` | false | Preserve Docker images (speeds up next `awake`) |

### What It Does

1. **Stops containers** — force-stops any running SAIP containers.
2. **Removes containers** — deletes container instances and anonymous volumes.
3. **Clears model cache** — removes downloaded weights and adapters from `~/.cache/saip/` (unless `--purge-cache=false`).
4. **Optionally removes images** — deletes SAIP Docker images (unless `--keep-images`).
5. **Reports cleanup** — lists removed resources and freed disk space.

### Example Output

```
$ saip down
[down] Stopping containers...
  ├─ saip-inference ... stopped and removed
  └─ saip-worker ... stopped and removed
[down] Removing model cache (~/.cache/saip/)...
  ├─ QuantTrio/Qwen3.5-4B-AWQ ... 5.7 GB removed
  ├─ adapters/general@000042 ... 128 MB removed
  └─ adapters/coding@000018 ... 96 MB removed
[down] Total freed: 4.4 GB
[down] Docker images preserved (use --keep-images=false to remove)
```

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | Teardown complete |
| 1 | Partial failure (some resources could not be removed; details in output) |

:::caution[Irreversible]
`saip down` deletes local model caches. The next `saip awake` will re-download everything from R2. Ensure your R2 credentials are valid before running `down`.
:::

## `saip status`

Display the current state of SAIP services, GPU, and configuration.

### Synopsis

```bash
saip status [--json] [--adapter-resolution <user>]
```

### Options

| Flag | Default | Description |
|------|---------|-------------|
| `--json` | false | Output as JSON (for scripting) |
| `--adapter-resolution <user>` | — | Show which adapter a specific user would receive |

### Output Format

```
$ saip status
[saip] Platform Status
─────────────────────
[sip] default (local): reachable=true mode=?
Mode:       TODO (awake / asleep / down)
Adapters:   3 defined (1 composite), registry valid
GPU:        NVIDIA GeForce RTX 3080 Laptop GPU — 16 GiB total, 13.07 GiB free, cc 8.6
Profile:    full-loop-12gb (auto-resolved), ceiling 11 GiB
            gpu_memory_utilization=0.6875 (derived), context 65536 tokens
Bucket:     saip-local
Uptime:     TODO
```

The `GPU` and `Profile` lines come from the same `ProfileService` resolution
`saip profiles` performs, so status and the tier report cannot disagree. When the card
cannot hold the resolved ceiling, the profile line is followed by
`NOT STARTABLE: insufficient_free_vram: …` naming the deficit.

:::caution[Not yet implemented]
These fields are still `TODO` in the shipped CLI and are shown as such rather than invented:
service mode (awake/asleep/down), uptime, GPU temperature and per-process utilization,
loaded-adapter names with their `@latest` resolution, and the last R2 sync timestamp. The
richer layout previously documented here was a design sketch, not output — it is why
`saip status` is the command to compare against `saip profiles` when the two look wrong.
:::

:::caution[Fields still TODO]
`saip status` prints host reachability, adapter registry validity, GPU + profile
resolution, and the configured bucket. It does **not** yet report: service mode
(awake/asleep/down), uptime, GPU temperature or per-process utilization, the adapters
currently loaded in the engine, the last R2 sync, or a rolling request rate — and there is
no `--json` output for status yet. `saip profiles --json` is the one command that does emit
machine-readable output today.
:::

### Adapter Resolution Check

```bash
$ saip status --adapter-resolution alice
Adapter resolution for 'alice':
  user mapping:  coding@latest
  resolved to:   coding@000018
  loaded:        yes
  source:        adapters.users.alice (overrides group: engineering)
```

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | Status retrieved (regardless of service state) |
| 1 | Cannot read configuration files |

:::note[Status Is Read-Only]
`saip status` never modifies state. It's safe to run at any time, including during `awake` or `sleep` transitions.
:::

## `saip profiles`

Show the hardware service profiles, which one this machine resolves to, and the engine
arguments that follow. Read-only: it probes the GPU and prints. It starts nothing.

### Synopsis

```bash
saip profiles [--profile <name>] [--json]
```

### Options

| Flag | Default | Description |
|------|---------|-------------|
| `--profile <name>` | auto-resolved | Resolve as if this tier were selected, to check whether the card can hold it and what it would run. |
| `--json` | false | Machine-readable output for scripting and CI. |

### What It Does

1. **Loads and validates the `profiles:` block** from `saip.yaml` through the same
   `ProfileService` the gateways use, so the CLI cannot disagree with the server about what a
   tier means.
2. **Probes the GPU** for name, total and free VRAM, and compute capability.
3. **Resolves the tier** — explicitly when `--profile` is given, otherwise the highest tier
   the card satisfies.
4. **Derives `gpu_memory_utilization`** from the tier ceiling over total VRAM and checks it
   against measured free memory, reporting the deficit rather than a start that would crash.
5. **Renders the implied engine arguments**, refusing to emit a KV-cache dtype this card
   cannot safely use.

### Example Output

```
$ saip profiles
[saip] GPU: NVIDIA GeForce RTX 3080 Laptop GPU — 16 GiB total, 13.46 GiB free, cc 8.6

  profile           min VRAM   min cc    ceiling  fits
  inference-8gb        8 GiB      7.5     7.0 GiB  yes
  full-loop-12gb      12 GiB      8.0    11.0 GiB  yes

[saip] Resolved: full-loop-12gb (auto)
[saip] Derived --gpu-memory-utilization=0.6875 (11 GiB ceiling / 16 GiB total)
[saip] Engine: --model QuantTrio/Qwen3.5-4B-AWQ --max-model-len 65536 --language-model-only
        --max-num-seqs 128 --enable-lora --max-loras 4 --max-lora-rank 16
```

When the card cannot hold the requested tier:

```
$ saip profiles --profile full-loop-12gb
[saip] GPU: NVIDIA GeForce RTX 2060 — 6 GiB total, 5.1 GiB free, cc 7.5
[saip] insufficient_vram: profile "full-loop-12gb" needs 12 GiB VRAM; this card has 6 GiB total
```

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | A profile resolved for this GPU |
| 1 | Configuration error (no `profiles:` block, invalid tier declaration) |
| 2 | No profile fits this GPU, or the GPU could not be read |

:::tip[Use it before buying hardware or booting]
`saip profiles` is the cheapest answer to "will this run here" — it reads the card and does
the arithmetic without pulling an image or loading weights. Run it on a candidate machine
before installing, and in CI to assert a target card satisfies a tier.
:::

:::note[Relationship to `awake`]
`saip awake` performs the same resolution and writes the derived engine arguments before
starting compose. `saip profiles` exists so that decision can be inspected — and tested
against a card — without changing anything.
:::

## `saip config`

Manage the encrypted local secret store. Values are written to `~/.saip/secrets.enc.json` —
outside the workspace — and resolved at runtime by the same provider chain the gateways use.

### Synopsis

```bash
saip config <init|list|get|set|unset|key|doctor> [name] [value] [--value <v>] [--stdin] [--reveal] [--force]
```

### Subcommands

| Form | Behavior |
|------|----------|
| `saip config list` | Names only, one per line. Never prints values. |
| `saip config get <name>` | Prints the value masked (`••••` plus length). `--reveal` prints it. |
| `saip config set <name>` | Prompts with echo disabled — keeps the secret out of shell history and `ps`. |
| `saip config set <name> --value <v>` | Non-interactive. Prefer piping: `printf %s "$V" \| saip config set NAME --stdin`. |
| `saip config unset <name>` | Removes it; reports whether it was present. |
| `saip config init` | Guided first-time setup: one value at a time, echo off, paste accepted, each prompt explaining purpose, scope, and where to create it. Questions are derived from your `saip.yaml`/`hosts.yaml`. `--force` re-asks everything. |
| `saip config help [name]` | Prints the credential catalog — purpose, how to create it, required scope, provider page — without prompting or writing anything. |
| `saip config forget <name>` | Removes the value from the encrypted store **and** `.env`, reporting each source. Use it when a stored value is wrong. |
| `saip config init --reset <name>` | Forgets one value and re-asks just that one. |
| `saip config key list` | Which unlock methods the store accepts and which one opened it just now. |
| `saip config key add <keyring\|unattended>` | Adds an unlock method. Never called for you. |
| `saip config key remove <id>` | Drops one; refuses to remove the last usable method, and deletes the `unattended` key file. |
| `saip config doctor` | Store path, file mode, wraps on file, **which wrap unlocked**, and a warning if an `unattended` wrap exists. |

Prompts read the controlling terminal (`/dev/tty`), not stdin, because `--stdin` supplies the value
through stdin. With no terminal the command refuses and prints the manual path rather than blocking.
`saip config init` cannot verify R2 credentials yet — the R2 client is separate work; see
[Managing Secrets](/saip/guides/manage-secrets/).

:::caution[Why `--value` is second choice]
A command-line argument is visible to every process on the machine via `ps` and lands in shell
history. `--stdin` and the interactive prompt exist so a secret never crosses the process
boundary as an argument. `--value` remains for scripting where the caller has already solved
that problem.
:::

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | Operation succeeded |
| 1 | Usage error, no key source available, or the store could not be decrypted |

:::note[Shell variables still win]
`saip config` writes the store, which sits **below** the parent environment in resolution order.
A variable you `export` in the same shell shadows the stored value, and `saip config doctor`
says so rather than leaving you to discover it.
:::
