SAIP requires several credentials for R2 storage, API authentication, and cloud provider access. This guide covers secure secret management across local and Hyperstack deployments.

## Setting Credentials

Shell environment variables are the most private mechanism — nothing touches the disk —
and they always win over every other source. They are not the most convenient for repeat use,
which is what the [encrypted store](#encrypted-local-store-recommended-for-real-deployments) is for. Set them in your current shell session or CI environment using `export`:

```bash
# === Cloudflare R2 (required) ===
export SAIP_R2_BUCKET="saip-platform"
export SAIP_R2_ENDPOINT="https://<account-id>.r2.cloudflarestorage.com"
export SAIP_R2_ACCESS_KEY_ID="abc123def456"
export SAIP_R2_SECRET_ACCESS_KEY="xyz789ghi012jkl345mno678pqr901stu234"

# === HuggingFace Hub (required for model downloads) ===
export SAIP_HF_TOKEN="hf_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"

# === Hyperstack (optional, remote deployments only) ===
export SAIP_HYPERSTACK_API_KEY="your-hyperstack-api-key"
export SAIP_HYPERSTACK_ENVIRONMENT="your-environment-name"
```

### Why Shell Variables Are Preferred

- **Never touch the filesystem** — credentials exist only in memory, so there is no file to accidentally commit, leak in a backup, or expose via misconfigured permissions.
- **Cannot be accidentally committed** — unlike `.env` files, there is nothing for `git add .` to pick up.
- **Automatically inherited by Docker Compose** — Compose inherits the parent shell's environment, so services receive these variables without any `env_file` configuration.
- **Standard across environments** — the same `export` commands work in your terminal, CI runners, and cloud instance user-data scripts.

To make exports persistent across terminal sessions, add them to your shell profile (`~/.bashrc`, `~/.zshrc`, etc.) or use a session manager like `direnv`.

## Alternative: `.env` Files (Local Development Only)

For local development convenience, you may optionally use a `.env` file instead of exporting variables manually. Copy the template and fill in your values:

```bash
cp .env.example .env
# Edit .env with your credentials
```

```ini
# === Cloudflare R2 (required) ===
SAIP_R2_BUCKET=saip-platform
SAIP_R2_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com
SAIP_R2_ACCESS_KEY_ID=abc123def456
SAIP_R2_SECRET_ACCESS_KEY=xyz789ghi012jkl345mno678pqr901stu234

# === HuggingFace Hub (required for model downloads) ===
SAIP_HF_TOKEN=hf_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

# === Hyperstack (optional, remote deployments only) ===
# SAIP_HYPERSTACK_API_KEY=your-hyperstack-api-key
# SAIP_HYPERSTACK_ENVIRONMENT=your-environment-name
```

:::caution[Never Commit `.env`]
The `.env` file contains secrets and must never be committed to version control. Verify it's in your `.gitignore`:

```bash
grep -q "^\.env$" .gitignore || echo ".env" >> .gitignore
```

Also ignore `.env.*` variants (`.env.local`, `.env.production`, etc.). **For production and CI, always use shell environment variables or a secrets manager instead.**
:::

### Required vs Optional Variables

All variables below can be set either as shell exports (`export SAIP_R2_BUCKET=...`) or in a `.env` file. Shell exports are recommended for all non-local environments.

| Variable | Required | Context |
|----------|----------|---------|
| `SAIP_R2_BUCKET` | ✅ Always | Target R2 bucket |
| `SAIP_R2_ENDPOINT` | ✅ Always | R2 API endpoint URL |
| `SAIP_R2_ACCESS_KEY_ID` | ✅ Always | R2 access key |
| `SAIP_R2_SECRET_ACCESS_KEY` | ✅ Always | R2 secret key |
| `SAIP_HF_TOKEN` | ⚠️ Optional | Only for gated repositories; public checkpoints work without it |
| `SAIP_HYPERSTACK_API_KEY` | ❌ Optional | Only for Hyperstack deployments |
| `SAIP_HYPERSTACK_ENVIRONMENT` | ❌ Optional | Only for Hyperstack deployments |

## Encrypted Local Store

Shell variables are the most *private* option but the least *durable*: they vanish when the shell
exits, they leak into `ps` and CI logs, and re-exporting them by hand is how credentials end up in
shell history. The store exists for durability, and the shell still wins where both provide a name.

### First-time setup: `saip config init`

`saip config set NAME` assumes you already know the name — that is the **reset** path. For a fresh
install there is a guided wizard:

```bash
saip config init
```

One value at a time, echo off, **clipboard paste works**, and each prompt explains what the value is
for, where to create it, and how to scope it. The questions are **derived from your configuration,
not a fixed list**: only credentials your `saip.yaml` / `hosts.yaml` actually reference are asked
about.

| Order | Value | Required | Where it is written |
|-------|-------|----------|---------------------|
| 1 | `SAIP_R2_BUCKET` | yes | `.env` — plain config, not a secret |
| 2 | `SAIP_R2_ENDPOINT` | yes | `.env` |
| 3 | `SAIP_R2_ACCESS_KEY_ID` | yes | encrypted store |
| 4 | `SAIP_R2_SECRET_ACCESS_KEY` | yes | encrypted store |
| 5 | `SAIP_HF_TOKEN` | optional, **always listed** — public checkpoints work without it | encrypted store |
| 6 | each declared `security.api_tokens[].token_secret` | required per token | encrypted store |
| 7 | `security.ui.admin_secret` | required only if configured | encrypted store |
| 8 | `SAIP_HYPERSTACK_API_KEY` | optional, **always listed** — only needed to deploy to cloud | encrypted store |
| 9 | `SAIP_HYPERSTACK_ENVIRONMENT` | optional, always listed | `.env` |
| 10 | `SAIP_SSH_PRIVATE_KEY` | optional, always listed — see the caveat below | encrypted store |

Those three are listed even when nothing references them yet, because they are the next
integrations to be built and a wizard that hides a credential until some other file mentions it is
not a wizard a new user can plan around.

**Caveat worth knowing before you test remote deploys:** the Hyperstack provider currently builds
its SSH argument as `-i /run/secrets/<key_secret>` — it uses the secret's *name* as a file path,
which nothing populates. Storing `SAIP_SSH_PRIVATE_KEY` therefore does **not** yet make remote SSH
work. Tracked separately; fixing it is a provider change, not a wizard change.

**Why secrets and non-secrets go to different places:** `${VAR}` interpolation reads the shell and
`.env`, never the store. Writing a bucket name into the store would report success and change
nothing, so the wizard puts interpolated values in `.env` (created `0600`) and name-resolved
credentials in the store.

Each item's explanation — what the value is for, how to create it, how to scope it, the provider page
and the docs link — prints **before** its prompt, on the same output stream as the prompt itself.
Showing `SAIP_R2_BUCKET:` alone and dumping the guidance afterwards defeats the purpose of the command.

**Behaviour:** guidance prints for **every** item, whether or not a value already exists — the
explanation is the reason to run the command, and suppressing it once something is set hides it
from exactly the person whose value is wrong. An already-set item names the **source** holding it
(`shell`, `.env`, or the encrypted store), so you know what to clear. Optional values skip on
empty; a required value given empty is re-asked once and then the
wizard stops rather than storing a blank; `Ctrl+C` cancels and exits **130**: every answer already given is already written (values are stored per item, not batched to the end, so a cancel cannot discard them) and the summary names what was stored and what is still unset. Ctrl+C needs explicit handling because raw mode disables `ISIG` — the keypress arrives as a byte, not a signal. ### Getting rid of a wrong value

`saip config forget NAME` removes the value from **both** places SAIP stores it — the encrypted
store and `.env` — and reports what it found in each. `saip config unset NAME` does the same thing;
it previously cleared only the store, so forgetting an interpolated value silently "succeeded" while
`init` went on seeing it.

```bash
saip config forget SAIP_R2_BUCKET          # clears .env
saip config init --reset SAIP_R2_BUCKET    # forget it, then re-ask just that one
saip config help SAIP_R2_BUCKET            # the guidance, without being prompted at all
saip config help                           # every item, with the current value's source
```

**A value in your shell cannot be forgotten by the CLI.** The shell wins the resolution chain, so
if `init` reports a value coming from `shell`, clear it yourself with `unset SAIP_R2_BUCKET` and
remove it from your shell profile — otherwise it reappears in the next session. `saip config
doctor` names any name shadowed this way.

`saip config help` exists because the wizard is the wrong place to read documentation you wanted
ten minutes ago: the same catalog, printed on demand, that never writes or prompts.

`saip config init --non-interactive` is the automation mode: it **prompts nothing and writes
nothing**, lists the required values that are still unset, prints the exact commands to set them,
and exits 1 if anything is missing (0 when the configuration is complete). With no controlling
terminal the interactive wizard **refuses immediately** rather than blocking forever on a prompt
nobody can answer — the failure #73 removed. `--force` re-asks everything.

:::note[What `init` does not do yet]
It cannot **verify** R2 credentials: the R2 client is separate work. `init` reports what it stored
and says verification is unavailable, rather than making an unsigned request that returns `403` for
a valid key and an invalid one alike. A check that cannot distinguish the two is not a check.
`saip config verify` ships with the storage provider.
:::

### Everyday commands

```bash
saip config set SAIP_R2_SECRET_ACCESS_KEY --stdin   # value piped; prompt is skipped
saip config set SAIP_R2_BUCKET --value saip-platform
saip config list                                    # names only, never values
saip config get SAIP_R2_ACCESS_KEY_ID               # masked unless --reveal
saip config key list                                # which unlock methods exist, which opened it
saip config key add unattended                      # opt-in convenience, see below
saip config key remove unattended
saip config doctor                                  # store path, wraps, unlocking method, warnings
```

Stdin is read **only with `--stdin`**. Auto-detecting "not a terminal" looks convenient and turns
any script, CI job, or agent that omits a value into a process waiting forever on input nobody will
send.

### How the key works

A random key (the KEK) encrypts your secrets and is **never stored** — it is kept once per unlock
method, wrapped under that method's own key. So:

- adding or removing an unlock method never re-encrypts your secrets;
- rotating a passphrase re-wraps only the KEK;
- there is **no password hash in the file**. The GCM tag on the wrapped KEK *is* the check, which
  also means a wrong passphrase and a tampered file are reported identically — the file cannot be
  used to probe guesses.

Creating a store prompts twice and confirms, because a mistyped passphrase would otherwise lock you
out of secrets that are unrecoverable by design. Prompts read the **controlling terminal**, not
stdin, since `--stdin` uses stdin for the value.

| Unlock method | Needs | Defends against |
|---|---|---|
| `passphrase` (default, always available) | typed per unlock | any reader without the passphrase, **including an agent with filesystem access** |
| `keyring` (`key add keyring`) | `secret-tool` (libsecret) installed | nothing stronger than an unlocked keyring — it buys no typing, not security |
| `unattended` (`key add unattended`) | a `0600` key file beside the store | repo-scoped readers and other users — **not** a process running as you |

`doctor` names the wrap that actually unlocked a read and warns while an `unattended` wrap exists, so
you never infer the wrong guarantee from the presence of a file.

### Resolution order

1. **Parent shell environment** — always wins, so `SAIP_R2_BUCKET=x saip ...` overrides without
   editing anything.
2. **`.env`** — folded in by the shared config loader (see
   [Configuration Reference](/saip/reference/configuration/)).
3. **Encrypted store**, for names the config resolves by secret name.
4. `MissingSecretError`, naming the secret. Silent empty values are never produced.

### What this does and does not protect

An agent or process running **as you, with read access to your home directory** can defeat the
`unattended` wrap and can read an exported `SAIP_SECRETS_PASSPHRASE`. The boundary drawn here is
exact: **workspace file access alone is not enough**, and a typed passphrase is the only tier that
also resists an agent running as you. A session keyring is reachable by anything in your unlocked
desktop session — that is what keyrings are for, which is why the keyring tier is labelled
convenience and not strength.

Headless SSH sessions often cannot reach the session bus at all. That is expected, not a flaw in the
design: type the passphrase, or export it from your CI secret store, which wins anyway.

:::note[Not yet: a managed secret manager]
`SecretsProvider` is the seam this sits behind, so OpenBao/Vault, or a cloud secret manager, can be
added as another source in the chain without touching any caller. Nothing here fetches from a remote
secret store yet.
:::

## Docker Compose Integration

Docker Compose **automatically inherits environment variables from the parent shell**. If you set credentials via `export` before running `docker compose up`, services receive them without any additional configuration:

```bash
# Credentials already exported in your shell — no env_file needed
export SAIP_R2_BUCKET="saip-platform"
export SAIP_R2_ENDPOINT="https://..."
export SAIP_R2_ACCESS_KEY_ID="..."
export SAIP_R2_SECRET_ACCESS_KEY="..."
export SAIP_HF_TOKEN="hf_..."

docker compose up -d
```

### Using `.env` Files with Compose (Local Development)

If you use a `.env` file instead of shell exports, reference it explicitly via `env_file`:

```yaml
services:
  inference:
    image: saip-inference:latest
    env_file:
      - .env
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]

  worker:
    image: saip-worker:latest
    env_file:
      - .env
```

:::note[Precedence]
Shell environment variables take precedence over `env_file` values. Variables set directly in the `environment:` block override both:

```yaml
services:
  inference:
    env_file: .env
    environment:
      - SAIP_NODE_ROLE=inference  # Overrides .env and shell value
```
:::

### Multiple Environment Files

For multi-environment local setups, layer environment files:

```yaml
services:
  inference:
    env_file:
      - .env                    # Base secrets (gitignored)
      - .env.local              # Local overrides (gitignored)
```

Files listed later take precedence. Keep shared non-secret config in a committed `.env.defaults` and secrets in the gitignored `.env`.

## Variable Interpolation in `saip.yaml`

SAIP supports `${VAR}` syntax in `saip.yaml` to inject environment variables at runtime:

```yaml
storage:
  r2:
    bucket: "${SAIP_R2_BUCKET}"
    endpoint: "${SAIP_R2_ENDPOINT}"
  huggingface:
    token_env: "SAIP_HF_TOKEN"
```

### Interpolation Syntax

| Syntax | Behavior |
|--------|----------|
| `${VAR}` | Replaced with the value of `VAR`; error if unset |
| `${VAR:-default}` | Replaced with `VAR` if set, otherwise `default` |
| `${VAR:?message}` | Replaced with `VAR` if set; prints `message` and exits if unset |

:::tip[Sensible Defaults]
Use `${VAR:-default}` for optional settings to avoid requiring every variable in `.env`:

```yaml
model:
  max_model_len: ${SAIP_MAX_MODEL_LEN:-65536}
```
:::

:::caution[No Nested Interpolation]
Variable references are resolved in a single pass. `${VAR_${OTHER}}` is not supported and will be treated as a literal string.
:::

## Rotating Credentials

### R2 Keys

1. Generate new keys in the Cloudflare R2 dashboard.
2. Update your credentials — re-export the shell variables or update your `.env` file.
3. Restart services: `saip sleep && saip awake`.
4. Delete the old keys in the R2 dashboard.

:::note[Zero-Downtime Rotation]
R2 supports multiple active access keys simultaneously. Add the new key first, verify SAIP works, then revoke the old key. This avoids downtime during rotation.
:::

### API Tokens

1. Generate a new token: `saip token generate --name rotated-2024-03`.
2. Update your credentials — re-export the shell variables or update your `.env` file and any client configurations.
3. Restart services.
4. Revoke the old token: `saip token revoke <old-token-id>`.

### Hyperstack API Keys

1. Generate a new key in the Hyperstack dashboard.
2. Update credentials on all nodes (shell exports, `.env`, or secrets manager).
3. Restart affected services.
4. Revoke the old key.

## Hyperstack Environment Injection

For remote deployments, inject secrets at instance creation time rather than copying `.env` files:

### Via Hyperstack Dashboard

1. Go to **Instances → Create Instance**.
2. Under **Advanced → User Data**, add environment exports:

```bash
#!/bin/bash
export SAIP_R2_BUCKET="saip-platform"
export SAIP_R2_ENDPOINT="https://..."
export SAIP_R2_ACCESS_KEY_ID="..."
export SAIP_R2_SECRET_ACCESS_KEY="..."
export SAIP_HF_TOKEN="hf_..."
```

:::caution[User Data Visibility]
Hyperstack user data is visible to anyone with dashboard access to the instance. For sensitive credentials, prefer the API injection method below or use a secrets manager.
:::

### Via Hyperstack API

Inject environment variables programmatically when creating instances:

```bash
hyperstack vm create \
  --name saip-inference \
  --image ubuntu-22.04-cuda-12.4 \
  --gpu rtx-a4000 \
  --env SAIP_R2_BUCKET="$SAIP_R2_BUCKET" \
  --env SAIP_R2_ENDPOINT="$SAIP_R2_ENDPOINT" \
  --env SAIP_R2_ACCESS_KEY_ID="$SAIP_R2_ACCESS_KEY_ID" \
  --env SAIP_R2_SECRET_ACCESS_KEY="$SAIP_R2_SECRET_ACCESS_KEY" \
  --env SAIP_HF_TOKEN="$SAIP_HF_TOKEN"
```

Variables injected this way are available in the instance's environment without writing a `.env` file to disk.

### Via Secrets Manager (Recommended for Production)

For production deployments, store secrets in a dedicated manager and fetch at boot:

```bash
# Example: fetch from HashiCorp Vault at instance startup
#!/bin/bash
vault kv get -format=json secret/saip/production | \
  jq -r 'to_entries[] | "export \(.key)=\(.value)"' > /etc/saip/env
source /etc/saip/env
rm /etc/saip/env
```

## CI/CD Environments

In continuous integration and deployment pipelines, always inject credentials as environment variables — never commit `.env` files or copy them to runners.

### GitHub Actions

Store secrets in your repository's **Settings → Secrets and variables → Actions**, then reference them in workflows:

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    env:
      SAIP_R2_BUCKET: ${{ secrets.SAIP_R2_BUCKET }}
      SAIP_R2_ENDPOINT: ${{ secrets.SAIP_R2_ENDPOINT }}
      SAIP_R2_ACCESS_KEY_ID: ${{ secrets.SAIP_R2_ACCESS_KEY_ID }}
      SAIP_R2_SECRET_ACCESS_KEY: ${{ secrets.SAIP_R2_SECRET_ACCESS_KEY }}
      SAIP_HF_TOKEN: ${{ secrets.SAIP_HF_TOKEN }}
    steps:
      - uses: actions/checkout@v4
      - run: docker compose up -d
```

GitHub masks secret values in logs automatically. Use [environment protection rules](https://docs.github.com/en/actions/deployment/targeting-different-environments/using-environments-for-deployment) to restrict access to production secrets.

### Hyperstack Deployments

For Hyperstack-managed instances, inject environment variables at creation time via the API or dashboard user-data script (see [Hyperstack Environment Injection](#hyperstack-environment-injection) above). This avoids writing secrets to disk entirely.

### Other CI Providers

The same principle applies universally: configure secrets in your CI provider's secret store and expose them as environment variables to the build/deploy job. Examples include GitLab CI/CD variables, CircleCI project environment variables, and Jenkins credentials bindings.

## Security Checklist

- [ ] Credentials set via shell exports or CI secrets (not committed files)
- [ ] If using `.env` locally, it is in `.gitignore`
- [ ] No secrets in committed files (check with `gitleaks` or `trufflehog`)
- [ ] R2 keys scoped to minimum required permissions
- [ ] API tokens rotated quarterly
- [ ] Hyperstack API keys restricted to necessary operations
- [ ] SSH keys use ed25519 or RSA-4096
- [ ] No secrets in Docker image layers (use runtime injection)
- [ ] Production secrets differ from development secrets
- [ ] CI/CD secrets stored in provider secret store, not in workflow files
