SAIP uses adapters (LoRA/QLoRA weight deltas) to specialize a base model for different tasks and users. This guide explains how to define adapters in the registry, compose weighted user adapters from components that train at different speeds, and configure user mappings, versioning, and resolution in `saip.yaml`. For the full field contract see [Adapter Definitions](/saip/reference/adapter-definitions/).

## The Adapter Registry

Adapters are defined once in the top-level `adapters:` array and referenced everywhere else — by users, by composites, by training jobs. Separating *adapter definitions* from *user mappings* is what lets one adapter be general-purpose (`global`), project-scoped (`project`), or personal (`user`).

```yaml
adapters:
  # Leaf adapters declare how they learn
  - name: coding
    scope: global
    description: "General software engineering behaviors"
    training:
      strategy: knowledge_embedding     # registered training strategy plugin
      data_scopes: [documents]          # Data API types that feed its training

  - name: treeseed-project
    scope: project
    project: treeseed
    training:
      strategy: corrective_sft
      data_scopes: [sessions, feedback]
```

Every leaf adapter names **one training strategy** and **the data scopes it consumes**. That linkage is the formal path from accumulated experience to updated weights: when you trigger a job against `treeseed-project`, the registry says which strategy plugin converts its linked sessions/feedback data into an Axolotl dataset — no guessing, no per-job re-specification (though jobs may override).

### Scopes

| Scope | Use for | Reuse rule |
|-------|---------|-----------|
| `global` | Shared capabilities everyone benefits from (coding, research) | Any user/composite can reference |
| `domain` | Knowledge domains without project ties | Any user/composite can reference |
| `project` | One project's conventions (`project:` required) | Only that project's users/composites |
| `user` | Personal preference/behavior adapters | Referenced by that user's mapping |

## Composing a User Adapter

A **composite adapter** merges several leaf adapters into one compiled artifact with two levels of control:

```yaml
adapters:
  - name: northstar-architect
    scope: user
    user: adrian
    trainable: false                    # derived, not trained directly
    composite:
      gain: 1.25                        # overall λ on the merged delta
      merge: weighted_linear            # PEFT merge algorithm
      components:
        - { adapter: coding, weight: 0.7 }
        - { adapter: treeseed-project, weight: 1.0 }
        - { adapter: research, weight: 0.45, version: "@000012" }
```

The math: `ΔW = gain × Σ(wᵢ · ΔWᵢ)` — each component contributes its own weight `wᵢ`, then the whole merged delta is scaled by `gain`. Both are independent knobs; treat `gain` as an evaluated hyperparameter (see [Adapter Composition](/saip/explanation/adapter-composition/)).

Why composites matter:

- **Independent cadences.** `coding` might promote daily from global documents; `treeseed-project` weekly from project sessions. The composite re-references current versions at compile time. Pin a component (`version: "@000012"`) when you need stability inside a fast-moving composition.
- **vLLM compatibility.** vLLM serves exactly one adapter per request, so the composition happens offline: the inference gateway compiles the weighted merge into a single named artifact published to R2. Inference sees `northstar-architect@000037` like any other adapter, and every compiled manifest records its component provenance.
- **Transparent user experience.** Adrian's requests resolve to his integrated adapter automatically; he never manages LoRA files. Meanwhile his sessions still flow to the right leaf (`treeseed-project`) because the training linkage lives on the leaves, not the composite.

:::caution[Composites Are Not Trainable]
Training jobs target leaf adapters only. Requesting a job against a composite returns `422`. Components are trained; composites are *derived*. Recompilation triggers automatically when a component promotes or the composition spec changes.
:::

## User Manifest Format

User-to-adapter mappings live in the top-level `users` array of `saip.yaml`. Each entry specifies separate adapters for inference and training — both reference names from the adapter registry:

```yaml
# User → adapter mapping (file-based for MVP)
users:
  - id: "default"
    adapters:
      inference: "default-agent@latest"   # a composite adapter
      training: "general"                  # a leaf adapter

  - id: "alice"
    adapters:
      inference: "coding@latest"
      training: "coding"
```

Each user entry has:
- **`id`** — the user identifier (use `"default"` for unauthenticated requests).
- **`adapters.inference`** — the adapter used for inference requests. May be any registry name, including composites.
- **`adapters.training`** — the leaf adapter that receives this user's training jobs (their experience data routes here via the adapter's declared linkage).

### Resolution Order

When a request arrives, the inference gateway resolves the adapter in this order:

1. **Explicit header** — `X-SAIP-Adapter: coding@000042` overrides everything.
2. **User mapping** — looked up from the authenticated user ID in the `users` array.
3. **Default** — falls back to the entry with `id: "default"`.

## Adapter Versioning Convention

Adapters follow a `<name>@<version>` naming scheme:

| Pattern | Meaning | Example |
|---------|---------|---------|
| `name@latest` | Resolves to the highest numbered version | `general@latest` → `general@000042` |
| `name@NNNNNN` | Pins to a specific 6-digit version | `coding@000018` |
| `name@base` | Uses the base model with no adapter | `general@base` |

### How `@latest` Resolves

The inference gateway scans the R2 adapter directory at startup and on each polling cycle:

```
adapters/
├── general@000040/
├── general@000041/
├── general@000042/    ← general@latest resolves here
├── coding@000017/
└── coding@000018/     ← coding@latest resolves here
```

Versions are zero-padded 6-digit integers, sorted lexicographically. This ensures `000042 > 000041` without numeric parsing.

:::caution[Version Gaps]
Version numbers don't need to be contiguous, but they must be monotonically increasing. Never reuse a version number — if `general@000042` was defective, publish `general@000043` instead of overwriting.
:::

## Adapter Aliasing (Runtime Resolution)

Adapter aliasing is a **runtime concept**, not a configuration field in `saip.yaml`. The inference gateway maintains an adapter index (`adapters/_index.json` in R2) that maps aliases to concrete versions:

```json
{
  "adapters": {
    "general@000042": { "id": "general@000042", "base_model": "Qwen/Qwen3.5-4B", ... },
    "coding@000018": { "id": "coding@000018", "base_model": "Qwen/Qwen3.5-4B", ... }
  },
  "aliases": {
    "general@latest": "general@000042",
    "coding@latest": "coding@000018"
  },
  "updated_at": "2025-01-15T10:00:00Z"
}
```

When `saip.yaml` references `general@latest`, the gateway resolves it through this index to the concrete version `general@000042`. This allows you to use stable names like `@latest` in your user mappings while the underlying version advances with each training run.

:::tip[Canary Deployments]
For gradual rollouts, pin specific users to a concrete version (e.g., `general@000040`) while others track `general@latest`. Update the alias in the R2 index when satisfied with the new version.
:::

## Adding New Users

To add a user to the system:

1. **Add to `saip.yaml`:**

```yaml
users:
  - id: "default"
    adapters:
      inference: "general@latest"
      training: "general"

  - id: "newuser"
    adapters:
      inference: "general@latest"
      training: "general"
```

2. **Reload configuration** (no restart needed):

```bash
saip reload
```

3. **Verify resolution:**

```bash
saip status --adapter-resolution newuser
# Output: newuser → general@latest → general@000042
```

## How the Inference Gateway Resolves Adapters

The gateway performs adapter resolution on every incoming request:

```
Request arrives
    │
    ▼
Has X-SAIP-Adapter header? ──Yes──► Load specified adapter
    │No
    ▼
Authenticated user ID? ──No──► Load default user's adapter
    │Yes
    ▼
User in users array? ──Yes──► Resolve user's adapters.inference
    │No
    ▼
Load default user's adapters.inference
```

### Hot Reloading

The gateway polls R2 every 60 seconds for new adapter versions. When a new version matching a `@latest` reference appears:

1. The new adapter weights are downloaded to local cache.
2. The vLLM engine loads the adapter in a background thread.
3. New requests route to the updated adapter; in-flight requests complete on the old version.
4. The old adapter is unloaded after a grace period.

:::note[Zero-Downtime Swaps]
Adapter hot-reloading is seamless — no requests are dropped during the transition. The swap typically takes 5–15 seconds depending on adapter size and network speed.
:::

## Complete Example

A production-ready registry + user configuration:

```yaml
adapters:
  - name: general
    scope: global
    training:
      strategy: knowledge_embedding
      data_scopes: [documents]

  - name: coding
    scope: domain
    training:
      strategy: corrective_sft
      data_scopes: [sessions, feedback]

  - name: research
    scope: domain
    training:
      strategy: weighted_kto
      data_scopes: [feedback]

  - name: treeseed-project
    scope: project
    project: treeseed
    training:
      strategy: corrective_sft
      data_scopes: [sessions, feedback]

  - name: northstar-architect
    scope: user
    user: adrian
    trainable: false
    composite:
      gain: 1.25
      components:
        - { adapter: coding, weight: 0.7 }
        - { adapter: treeseed-project, weight: 1.0 }
        - { adapter: research, weight: 0.45 }

users:
  - id: "default"
    adapters:
      inference: "general@latest"
      training: "general"

  - id: "alice"
    adapters:
      inference: "coding@latest"
      training: "coding"

  - id: "bob"
    adapters:
      inference: "general@000040"     # pinned known-good version
      training: "general"

  - id: "adrian"
    adapters:
      inference: "northstar-architect@latest"
      training: "treeseed-project"
```

In this setup:
- **Adrian** gets his compiled composite (coding × 0.7, project × 1.0, research × 0.45, gain 1.25) for transparent inference, while his project sessions train the `treeseed-project` leaf directly.
- **Alice** uses `coding@latest` for both paths; her feedback trains the same leaf everyone shares.
- **Bob** is pinned to `general@000040` for inference (a known-good version).
- **Unauthenticated requests** fall back to the `default` user's `general@latest`.

:::note[Adapter Aliasing]
The `@latest` suffix is resolved at runtime through the adapter index in R2 (`adapters/_index.json`). See [Adapter Aliasing](#adapter-aliasing-runtime-resolution) above for details.
:::
