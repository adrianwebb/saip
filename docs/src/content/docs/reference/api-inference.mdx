The inference gateway listens on the port configured in `inference.port` (default `8000`). All endpoints accept and return JSON unless noted otherwise.

Base URL: `http://<host>:<inference.port>`

The API is organized into three surfaces:

- **Chat Completions** (`/v1/chat/*`) — OpenAI-compatible model inference with adapter selection
- **SystemOne** (`/v1/systemone/*`) — Grammar-constrained structured output generation
- **Data API** (`/v1/data/*`) — Document upload, processing, session history, and feedback ingestion

## Authentication

Every mutating/serving route (chat, systemone, data) is protected by a pluggable
[AuthProvider](/saip/reference/security-model/) configured under `security:` in `saip.yaml`.

- Send `Authorization: Bearer <token>`; the token maps to a caller identity via named secrets.
- The resolved caller selects their configured adapter automatically.
- **Fail-closed:** unless `security.dev_mode` is explicitly `true`, a request without a valid bearer token is rejected with `401`. There is no silent fallback to an anonymous/default user on protected routes.
- `GET /health` stays public for liveness checks.

:::note[Development]
Set `security.dev_mode: true` to authenticate all requests as a single `dev` principal during local development. Never use it in production.
:::

## POST /v1/chat/completions

OpenAI-compatible chat completion endpoint. Automatically selects the caller's configured adapter based on authentication context.

### Request Headers

| Header          | Required | Description                                       |
|-----------------|----------|---------------------------------------------------|
| `Authorization` | Yes      | `Bearer <token>` identifying the caller.          |
| `Content-Type`  | Yes      | `application/json`                                |

### Request Body

| Field            | Type       | Required | Description                                                      |
|------------------|------------|----------|------------------------------------------------------------------|
| `model`          | `string`   | No       | Adapter ID override. Omit to use the caller's default adapter.   |
| `messages`       | `Message[]`| Yes      | Array of chat messages (`role`, `content`).                      |
| `temperature`    | `number`   | No       | Sampling temperature. Default `1.0`.                             |
| `max_tokens`     | `number`   | No       | Maximum tokens in the response.                                  |
| `top_p`          | `number`   | No       | Nucleus sampling threshold.                                      |
| `stream`         | `boolean`  | No       | If `true`, response is SSE. Default `false`.                     |
| `stop`           | `string \| string[]` | No | Stop sequences.                                        |

### Response (non-streaming)

```json
{
  "id": "chatcmpl-abc123",
  "object": "chat.completion",
  "created": 1705312200,
  "model": "general@000042",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "Response text here."
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 42,
    "completion_tokens": 128,
    "total_tokens": 170
  }
}
```

### Response (streaming)

Server-Sent Events with `data:` lines containing partial `chat.completion.chunk` objects. Final chunk includes `[DONE]`.

### Example

```bash
curl -X POST http://localhost:8000/v1/chat/completions \
  -H "Authorization: Bearer $SAIP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [
      {"role": "user", "content": "What is SAIP?"}
    ],
    "temperature": 0.7
  }'
```

## SystemOne Endpoints

Available only when `inference.systemone.enabled` is `true`. These endpoints provide structured output generation using grammar-constrained decoding.

### POST /v1/systemone/completions

Generates structured output conforming to a provided JSON schema or grammar.

#### Request Body

| Field      | Type     | Required | Description                                              |
|------------|----------|----------|----------------------------------------------------------|
| `messages` | `Message[]` | Yes   | Chat messages providing context.                         |
| `schema`   | `object` | Yes      | JSON Schema defining the expected output structure.      |
| `grammar`  | `string` | No       | GBNF grammar string (alternative to `schema`).           |
| `model`    | `string` | No       | Adapter ID override.                                     |

#### Response

```json
{
  "id": "sysone-abc123",
  "object": "systemone.completion",
  "created": 1705312200,
  "model": "general@000042",
  "output": {
    "field1": "value1",
    "field2": 42
  },
  "valid": true
}
```

#### Example

```bash
curl -X POST http://localhost:8000/v1/systemone/completions \
  -H "Authorization: Bearer $SAIP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "messages": [
      {"role": "user", "content": "Extract entities from: John works at Acme Corp."}
    ],
    "schema": {
      "type": "object",
      "properties": {
        "person": {"type": "string"},
        "organization": {"type": "string"}
      },
      "required": ["person", "organization"]
    }
  }'
```

# Data API

The Data API handles document upload, processing, session history ingestion, and feedback collection. Document processor plugins run within the inference gateway because they may require model inference — OCR via Marker for PDFs, code analysis, structured extraction. Processed data is written to R2 object storage, where the training gateway reads it for fine-tuning jobs.

### Document Processor Plugins

| Plugin | Accepts | Processing |
|--------|---------|------------|
| `markdown-processor` | `.md`, `.mdx` files | Structured text with heading hierarchy |
| `code-processor` | Source code files | Language-tagged code with file structure metadata |
| `pdf-processor` | PDF documents | Text extraction via Marker OCR with section boundaries |
| `jsonl-processor` | JSONL datasets | Validated record sequences |
| *(extensible)* | *(new formats)* | *(canonical intermediate format)* |

Each data type plugin registers its own endpoint under `/v1/data/<name>` with standard CRUD operations. When you install a new data type plugin, it registers its own endpoint path, declares its processor function, and specifies which training strategies can consume its output. No changes to the gateway core are needed.

## POST /v1/data/documents

Submit a document for processing. The registered document processor plugins handle format-specific conversion. Documents that require model-assisted processing (e.g., PDF OCR via Marker) are processed inline since the inference gateway has access to the model backend.

### Request Headers

| Header         | Required | Description              |
|----------------|----------|--------------------------|
| `Content-Type` | Yes      | `application/json`       |

### Request Body

| Field         | Type                                | Required | Description                                |
|---------------|-------------------------------------|----------|--------------------------------------------|
| `source`      | `string`                            | Yes      | Origin URI or description.                 |
| `source_type` | `'document' \| 'repository' \| 'dataset'` | Yes | Source classification.              |
| `content`     | `string`                            | Yes      | Raw document content.                      |
| `license`     | `string`                            | No       | SPDX license identifier.                   |
| `tags`        | `string[]`                          | No       | Classification tags.                       |

### Response `201 Created`

```json
{
  "id": "doc-20250115-001",
  "source": "internal-wiki/onboarding.md",
  "source_type": "document",
  "hash": "sha256:a1b2c3...",
  "size_bytes": 4096,
  "processed_by": "markdown-processor",
  "created_at": "2025-01-15T10:30:00Z"
}
```

### Example

```bash
curl -X POST http://localhost:8000/v1/data/documents \
  -H "Content-Type: application/json" \
  -d '{
    "source": "internal-wiki/onboarding.md",
    "source_type": "document",
    "content": "# Onboarding Guide\n...",
    "tags": ["onboarding", "hr"]
  }'
```

## POST /v1/data/feedback

Submit a feedback record linked to a session. Used as reward signal for weighted KTO and corrective SFT training strategies. Feedback is stored in R2 for the training gateway to consume.

### Request Body

| Field           | Type                      | Required | Description                                            |
|-----------------|---------------------------|----------|--------------------------------------------------------|
| `session_id`    | `string`                  | Yes      | Session this feedback refers to.                       |
| `message_id`    | `string`                  | No       | Specific message within the session.                   |
| `reward`        | `number`                  | Yes      | Scalar reward (must be within configured `reward_range`). |
| `confidence`    | `number`                  | No       | Confidence weight (0–1).                               |
| `dimensions`    | `Record<string, number>`  | No       | Multi-dimensional reward breakdown.                    |
| `feedback_text` | `string`                  | No       | Free-form human commentary.                            |

### Response `201 Created`

```json
{
  "id": "fb-20250115-001",
  "session_id": "sess-abc123",
  "reward": 2,
  "confidence": 0.9,
  "created_at": "2025-01-15T11:00:00Z"
}
```

### Example

```bash
curl -X POST http://localhost:8000/v1/data/feedback \
  -H "Content-Type: application/json" \
  -d '{
    "session_id": "sess-abc123",
    "reward": 2,
    "confidence": 0.9,
    "feedback_text": "Accurate and well-structured response."
  }'
```

## Error Responses

All endpoints return standard HTTP error codes with a JSON body:

```json
{
  "error": {
    "message": "Description of the error",
    "type": "invalid_request_error",
    "code": "adapter_not_found"
  }
}
```

| Status | Code                  | Meaning                                                        |
|--------|-----------------------|----------------------------------------------------------------|
| `400`  | `invalid_request`     | Malformed request or invalid parameters.                       |
| `401`  | `unauthorized`        | Missing or invalid authorization.                              |
| `404`  | `adapter_not_found`   | Requested adapter, document, session, or resource not found.   |
| `422`  | `reward_out_of_range` | Reward outside configured `reward_range`.                      |
| `429`  | `rate_limited`        | Rate limit exceeded.                                           |
| `500`  | `internal_error`      | Bug inside SAIP (adapter load failure, R2 write failure).      |
| `502`  | `backend_error`       | The inference engine is unreachable or returned an error status. The engine's own message is forwarded; this is not retried. |
| `503`  | `backend_unavailable` | No engine is attached (`SAIP_VLLM_BASE_URL` unset) or GPU offline. |
| `504`  | `backend_timeout`     | The engine did not answer within `SAIP_VLLM_TIMEOUT_MS`.       |

:::note[Why 502 and 504 are separated from 500]
A slow prefill on an 8 GB card, a crashed engine container, and a defect in the gateway all
look identical from a `500`. Distinguishing them matters operationally: `502`/`504` mean the
model server needs attention (`docker compose logs vllm`), while `500` means SAIP itself does.
Requests are **not** retried on a backend error, because resending a generation can duplicate
recorded sessions.
:::
